> 2026년 10월에 블로그를 새로 정리하면서, 이 도구로 만든 논문 리뷰들도 원문 초록과 다시 대조해 고쳐 썼습니다. 아래 내용은 도구를 처음 만들었을 때의 기록입니다.

## 왜 만들었나

논문 리뷰는 늘 같은 곳에서 시간이 듭니다. PDF를 열고, 초록과 실험을 다시 읽고, 블로그 형식에 맞추고, 마지막으로 블로그 저장소에 옮기는 일이 매번 반복됩니다. 하나하나는 어렵지 않지만 손이 많이 갑니다.

그래서 이 반복을 줄이는 작은 작업용 도구를 만들었습니다. 목표는 논문을 넣으면 바로 게시해 버리는 자동 요약기가 아니라, **초안을 빠르게 만들고 사람이 손볼 곳을 분명히 남겨 주는** 글쓰기 보조 도구입니다. 코드는 [paper-blog-toolkit](https://github.com/Kkubuck/paper-blog-toolkit) 저장소에 있습니다.

## 구조를 먼저 잡은 이유

이 도구에서 중요한 건 어떤 LLM을 붙였는가보다, 논문을 블로그 글로 바꾸는 흐름을 얼마나 다루기 좋게 나눴는가였습니다. 그래서 Codex가 읽고 고치기 좋은 구조를 먼저 정했습니다.

- 입력: PDF, arXiv ID, arXiv URL, 주제
- 출력: 블로그 포스트, 논문 목록 페이지, 논문별 자료 폴더
- 게시: 새로 생성된 파일만 골라 `git add → commit → push`
- 수정: 긴 본문을 통째로 다시 쓰지 않고 섹션 단위로 보강

이렇게 해 두면 Codex로 고치든 직접 고치든 어디를 건드려야 하는지가 분명해집니다.

## 내부 구성

명령줄 도구 `paper-blog` 하나로 시작하지만, 안쪽은 역할이 나뉘어 있습니다.

| 파일 | 역할 |
| --- | --- |
| `cli.py` | 어떤 작업을 할지 받는 입구 |
| `pipeline.py` | 추출, 초안 생성, 검수, 렌더링을 묶는 중심 흐름 |
| `render.py` | 블로그 포스트와 목록 페이지를 출력 |
| `publish.py` | 생성된 파일만 골라 Git으로 올리는 게시 단계 |

특히 마음에 드는 부분은 `publish.py`입니다. 저장소 전체를 올리지 않고 방금 생성된 포스트와 목록 파일만 추적해 커밋하기 때문에, 글 하나를 올릴 때 블로그의 다른 작업과 섞이지 않습니다.

## 사용법

실제로 쓰는 명령은 몇 개 되지 않습니다.

```bash
# 환경 점검
paper-blog doctor

# 논문 한 편으로 초안 만들기
paper-blog draft --arxiv-id 2509.15753 --site-dir /path/to/Kkubuck.github.io

# 큐레이션 파일로 여러 편을 한 번에 만들기
paper-blog compose --input examples/cod_top20_recent_plus_benchmarks.json --site-dir /path/to/Kkubuck.github.io

# 이미 올린 글의 섹션 보강하기
paper-blog expand-sections --site-dir /path/to/Kkubuck.github.io --cache-dir downloads/tablecheck
```

게시까지 한 번에 하려면 마지막에 `--publish`를 붙입니다.

```bash
paper-blog draft --arxiv-id 2509.15753 --site-dir /path/to/Kkubuck.github.io --publish
```

인터페이스를 이 정도로 줄여 두니 도구가 커져도 사용법은 복잡해지지 않았습니다.

## Codex와 잘 맞는 이유

작업하면서 느낀 점은, Codex가 잘 돕는 일은 화려한 추론보다 **입출력 약속이 분명한 반복 작업**이라는 것입니다.

- 논문을 넣으면 포스트 파일이 생기는 위치가 정해져 있고
- 목록 파일이 갱신되는 위치도 정해져 있고
- 게시 단계가 어떤 파일만 올리는지 코드에 드러나 있고
- 이미 만든 글을 보강하는 경로도 따로 있습니다.

어디를 어떻게 바꿔야 하는지 드러나 있으니 Codex로 작업할 때도 안정적입니다. 거대한 스크립트 하나였다면 글의 말투만 바꾸거나 게시 흐름만 고치기가 훨씬 어려웠을 겁니다.

## 글을 만들 때의 기준

처음에는 그림을 자동으로 넣고 검수 로그도 공개 글에 보여 주는 방향까지 시도했습니다. 그런데 블로그에서 읽히는 글은 생각보다 단순해야 했습니다. 지금은 다음 기준을 따릅니다.

- 공개 글에는 내부 로그를 보이지 않는다.
- 본문은 한국어로 쓴다.
- 초록·서론·방법·실험처럼 논문의 섹션 구조가 드러나게 나눈다.
- 성능 비교는 이미지보다 표로 다시 적는 편이 읽기 좋으면 표를 쓴다.

## 블로그와 도구 저장소를 나눈 이유

처음에는 블로그와 도구를 한 저장소에 두려고 했습니다. 막상 그렇게 하니 블로그는 도구 소개 페이지처럼 보이고, 도구 저장소는 문서와 코드가 섞여 흐릿해졌습니다. 그래서 블로그 저장소는 글과 페이지, 도구 저장소는 코드와 테스트와 예시 입력이 중심이 되도록 나눴습니다. 블로그는 읽는 곳이고 도구 저장소는 만드는 곳이라는 구분이 훨씬 선명해졌습니다.

## 앞으로 손볼 부분

- 표를 자동으로 다시 만드는 부분이 더 안정적이어야 합니다.
- 분야가 다른 논문에서도 본문 말투가 덜 흔들려야 합니다.
- 게시 전에 사람이 마지막으로 확인하기 좋은 미리보기가 필요합니다.

완벽하진 않지만, 논문을 읽고 블로그에 올리는 일이 메모와 로컬 파일과 블로그 저장소 사이에서 흩어지지 않고 하나의 흐름으로 이어졌다는 점에서 의미 있는 첫 버전이라고 생각합니다.
